# 0016: Redis 장애 시 정책 — 보안 체크는 fail-closed, 캐시는 DB로 저하

## 상태

Accepted

## 배경

`sendMessage`/인증 요청 경로에서 Redis는 위험도가 서로 다른 여러 지점을 떠받칩니다.
레이트리밋 카운터와 토큰 블랙리스트 체크는 DB에 대체 경로가 없고, 밴/뮤트 게이트 중 뮤트는
DB에 대체 경로가 없으며 차단은 별도 기록이 이미 있습니다. 반면 `user_cache`는 기존 DB 조회
앞에 놓인 읽기 전용 캐시일 뿐입니다. 이번 작업 전에는 Redis 호출의 에러 처리가 일관되지
않았고 대부분은 아예 없었습니다. `RateLimitGuard`만 Redis 에러를 명시적으로 잡아서 요청을
거부했고(`rate-limit.guard.ts:70-82`), `ModerationService.isMuted()`와 `JwtStrategy.validate()`의
Redis 읽기 두 곳은 에러 처리가 전혀 없어서, 예기치 못한 Redis 장애가 나면 예외가 그대로
전파되어 `AllExceptionsFilter`를 거쳐 정책과 무관한, 문서화되지 않은 `500`으로 노출됐습니다.
결국 Redis 장애 시 실제 동작이 "어느 호출이 먼저 실패하느냐"에 따라 달라졌고, "Redis가 죽으면
어떻게 되는가"에 대한 문서화된 단일한 답이 없었습니다.

## 결정

호출 지점마다 Redis 밖에 믿을 수 있는 폴백이 있는지에 따라 두 정책 중 하나를 적용합니다.

- **Fail closed(폴백 없음)** — 잡히지 않은 예외가 무관한 `500`으로 새어나가게 두는 대신,
  체크가 직접 요청을 거부합니다:
  - `RateLimitGuard`(`rate-limit.guard.ts:70-82`, 기존 코드): 에러를 잡아 로그를 남기고
    `false`를 반환해 요청을 거부합니다.
  - `JwtStrategy`의 블랙리스트 체크(`jwt.strategy.ts:37-50`): 에러를 잡아 로그를 남기고
    `UnauthorizedException`을 던집니다. 실제로 블랙리스트에 오른 토큰과 결과는 같지만,
    로그로 원인을 추적할 수 있다는 점이 다릅니다.
  - `ModerationService.isMuted()`(`moderation.service.ts:94-105`): 에러를 잡아 로그를 남기고
    `true`(뮤트로 간주)를 반환합니다. `ModerationGuard`가 이미 `true` 결과를
    `ForbiddenException`으로 바꿔주므로 가드 쪽 수정은 필요 없습니다.

- **기존 DB 폴백으로 저하(캐시 전용 읽기이고 DB가 원본인 경우)** — `JwtStrategy`의
  `user_cache` 읽기/쓰기(`jwt.strategy.ts:61-71, 90-102`): 읽기에서 Redis 에러가 나면 캐시
  미스와 똑같이 취급합니다(`cached`가 `null`로 유지됨). 그러면 같은 메서드 안에 이미 있는 DB
  조회 경로로 자연스럽게 넘어갑니다. 쓰기(캐시 저장)에서 나는 Redis 에러는 로그만 남기고
  무시합니다. 호출자는 이미 DB에서 조회한 유저를 들고 있으므로, 캐시 쓰기 실패가 요청 자체를
  실패시켜서는 안 되기 때문입니다.

**고려했다가 배제한 대안:**

- **Redis 에러 시 어디서든 fail-open**: 배제했습니다. 하필 Redis 장애 시점 — 정상 트래픽
  복구와 어뷰징을 구분하기 가장 어려운 순간 — 에 레이트리밋과 뮤트/차단 게이트를 그대로
  통과시키게 됩니다. 불확실한 상황에서 보안 체크가 해야 할 일과 정반대입니다.
- **`user_cache`까지 포함해 어디서든 fail-closed**: 특히 `user_cache`에 대해서는
  배제했습니다. 같은 메서드 안에 이미 DB 폴백이 있는데 캐시 전용 읽기 하나 때문에 인증 요청
  전체를 실패시키는 것은, "미스로 취급"하는 저하 방식보다 명백히 나쁩니다. 저하 방식은
  사용자가 체감하는 비용 없이 같은 수준의 안전을 달성합니다.

## 결과

- 보안과 관련된 가드나 전략(strategy)에 새 Redis 호출을 추가할 때는 반드시 try/catch로
  감싸고, 믿을 수 있는 폴백이 있는지에 따라 위 두 정책 중 하나를 명시적으로 골라야 합니다.
  보안 관련 Redis 읽기를 무방비로 두어 예기치 못한 에러가 일반적인 `500`으로 새게 놔두면
  안 됩니다.
- 같은 메서드 안에 이미 DB(또는 다른 믿을 수 있는) 폴백 경로가 있는 캐시 전용 읽기는 "에러를
  미스로 취급"하는 패턴을 재사용해야 합니다. 기능적으로 캐시 미스와 동일한 상황에 새 실패
  모드를 만들면 안 됩니다.
- DB에 대체 경로 없이 Redis에만 기대는 보안 체크(예: 뮤트 상태, 토큰 블랙리스트)는 명시적으로
  fail-closed여야 합니다. 잡히지 않은 예외가 우연히 거부로 이어지는 것은 문서화된
  fail-closed 정책과 같지 않습니다. HTTP 상태 코드와 로그 형태가 다르고, 스택 트레이스를
  읽지 않는 한 "Redis가 죽었다"는 원인으로 되짚을 수 없기 때문입니다.
