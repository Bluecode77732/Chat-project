# 0016: Redis 장애 시 정책 — 보안 체크는 fail-closed, 캐시는 DB로 저하

## 상태

Accepted

## 배경

`sendMessage`/인증 요청 경로에서 Redis는 위험도가 서로 다른 여러 호출 지점을 뒷받침합니다: DB
대응물이 없는 레이트리밋 카운터, DB 대응물이 없는(뮤트) 혹은 별도로 이미 존재하는(차단) 밴/뮤트
게이트, DB 대응물이 없는 토큰 블랙리스트 체크, 그리고 기존 DB 조회 앞단에 있는 읽기 전용 캐시인
`user_cache`. 이번 작업 이전에는 Redis 호출의 에러 처리가 일관되지 않았고 대부분 아예 없었습니다:
`RateLimitGuard`는 Redis 에러를 명시적으로 잡아서 요청을 거부했지만(`rate-limit.guard.ts:70-82`),
`ModerationService.isMuted()`와 `JwtStrategy.validate()`의 두 Redis 읽기는 에러 처리가 전혀 없어서,
예기치 못한 Redis 장애가 나면 잡히지 않고 전파되어 `AllExceptionsFilter`를 통해 정책과 무관한, 문서화
안 된 `500`으로 노출되었습니다. 즉 Redis 장애 시 실제 동작은 어느 호출이 먼저 실패하느냐에 달려
있었고, "Redis가 죽으면 어떻게 되는가"에 대한 단일한 문서화된 답이 없었습니다.

## 결정

호출 지점마다 Redis 아닌 권위 있는 폴백이 존재하는지에 따라 두 가지 정책 중 하나를 적용합니다.

- **Fail closed(폴백 없음)** — 잡히지 않은 예외가 무관한 `500`으로 새어나가게 두는 대신, 체크가
  요청을 거부합니다:
  - `RateLimitGuard`(`rate-limit.guard.ts:70-82`, 기존 코드): 에러를 잡아 로그를 남기고 `false`를
    반환(요청 거부)합니다.
  - `JwtStrategy`의 블랙리스트 체크(`jwt.strategy.ts:37-50`): 에러를 잡아 로그를 남기고
    `UnauthorizedException`을 던집니다 — 실제로 블랙리스트에 오른 토큰과 결과는 같지만, 로그로
    원인을 추적할 수 있습니다.
  - `ModerationService.isMuted()`(`moderation.service.ts:94-105`): 에러를 잡아 로그를 남기고
    `true`(뮤트로 간주)를 반환합니다 — `ModerationGuard`가 이미 `true` 결과를 `ForbiddenException`으로
    바꿔주므로 가드 쪽 수정은 필요 없습니다.

- **기존 DB 폴백으로 저하(캐시 전용 읽기이면서 DB가 진실 공급원인 경우)** — `JwtStrategy`의
  `user_cache` 읽기/쓰기(`jwt.strategy.ts:61-71, 91-101`): 읽기 시 Redis 에러는 캐시 미스와 동일하게
  취급되어(`cached`가 `null`로 유지됨) 같은 메서드 안에 이미 있는 DB 조회 경로로 자연스럽게
  흘러갑니다. 쓰기(캐시 저장) 시 Redis 에러는 로그만 남기고 무시됩니다 — 호출자는 이미 DB에서 조회한
  유저를 갖고 있고, 캐시 쓰기 실패가 요청 자체를 실패시켜서는 안 되기 때문입니다.

## 결과

- 보안과 관련된 가드나 전략(strategy)에 새로운 Redis 호출을 추가할 때는 반드시 try/catch로 감싸고,
  권위 있는 폴백이 있는지에 따라 위 두 정책 중 하나를 명시적으로 골라야 합니다 — 보안 관련 Redis
  읽기를 무방비로 두고 예기치 못한 에러가 일반적인 `500`으로 새게 놔두면 안 됩니다.
- 같은 메서드 안에 이미 DB(또는 다른 권위 있는) 폴백 경로가 있는 캐시 전용 읽기는 "에러를 미스로
  취급"하는 패턴을 재사용해야 하며, 기능적으로 캐시 미스와 동일한 상황에 대해 새로운 실패 모드를
  만들어내면 안 됩니다.
- DB 대응물이 없이 Redis에만 의존하는 보안 체크(예: 뮤트 상태, 토큰 블랙리스트)는 명시적으로
  fail-closed 해야 합니다 — 잡히지 않은 예외가 우연히 거부로 이어지는 것에 의존하는 건 문서화된
  fail-closed 정책과 같지 않습니다. 정확한 HTTP 상태 코드와 로그 형태가 다르고, 스택 트레이스를 읽지
  않는 이상 "Redis가 죽었다"는 원인으로 귀속시킬 수 없기 때문입니다.
