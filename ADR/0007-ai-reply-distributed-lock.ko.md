# 0007: AI 답장 생성을 위한 룸 단위 분산 락

## 상태

Accepted

## 배경

동일한 AI 동반자 룸에 연속으로 도착하는 두 메시지(예: 클라이언트 재시도, 혹은 탭 두 개)가 각각
독립적으로 `AiService.handleReply()`를 트리거할 수 있고, 이는 원래 한 번의 대화 턴이어야 할 것에
대해 Gemini API 호출 두 번과 AI 답장 두 개를 만들어버릴 수 있습니다.

## 결정

`AiService.handleReply()`는 답장을 생성하기 전에 원자적인 Redis 락을 획득합니다:
`SET ai:lock:{roomId} 1 EX 30 NX`(`ai.service.ts:115-122`; TTL은 `AI_LOCK_TTL_SECONDS` 상수,
`ai.service.ts:22`). `SET ... NX`가 락 획득에 실패하면(이미 락이 걸려 있으면) 큐잉하지 않고 즉시
로그를 남기고 반환합니다(`ai.service.ts:124-127`) — 답장을 건너뛰는 것이지, 큐에 넣는 게 아닙니다.
락은 `finally` 블록(`ai.service.ts:196`)에서 해제되므로 답장 생성 중 예외가 나도 반드시 풀립니다.
- 고려했다가 배제한 대안:
  - **원자적이지 않은 check-then-set**(`GET`으로 확인 후 `SET`): 배제 — 두 명령 사이의 틈이 바로
    거의 동시에 도착하는 두 트리거가 부딪히는 그 지점이라, 이 락이 막으려는 중복 답장 버그가 다시
    열립니다.
  - **Redis 키 대신 DB 레벨 락**(예: 룸 행에 `SELECT ... FOR UPDATE`): 배제 — 네트워크에 의존하는
    Gemini API 호출은 몇 초씩 걸릴 수 있는데, 그동안 DB 커넥션과 트랜잭션을 계속 붙잡고 있게
    됩니다. Redis 키는 가벼운 `SET`/`DEL` 한 쌍만으로 유지됩니다.
  - **전역 락**(룸 단위가 아님): 배제 — 실제 경합은 룸 하나 안에서만 존재하는데, 앱 전체의 관련
    없는 모든 룸의 AI 답장을 이유 없이 직렬화시켜 버립니다.

## 결과

- 이와 비슷한 리소스 단위 락에 대해 원자적이지 않은 check-then-set(`GET` 후 `SET`)은 절대
  제안하지 않습니다 — 이 패턴이 애초에 막으려던 레이스가 다시 열립니다. `SET ... NX`(또는 그에
  준하는 원자적 프리미티브)가 필수입니다.
- 이 락은 *skip*이지 *queue*가 아닙니다 — 락이 걸려 있는 동안 두 번째 트리거가 오면 답장을 아예
  받지 못하며, 지연된 답장을 받는 게 아닙니다. 이는 채팅 UX를 위해 받아들인 트레이드오프입니다(맥락에서
  벗어난 지연된 중복 답장은 조용한 건너뜀보다 나쁩니다). 큐잉 시맨틱이 필요한 향후 기능은 락을 더
  오래 잡는 방식이 아니라 다른 메커니즘(예: 잡 큐)이 필요합니다.
- 30초 TTL은 프로세스가 크래시해서 락이 영원히 잡혀 있는 상황을 막기 위한 안전망이며, 정상적인
  경우에 도달하도록 의도된 값이 아닙니다(Gemini 호출은 그보다 훨씬 빨리 끝날 것으로 예상됩니다).
  향후 일반적인 답장 지연 시간이 늘어난다면(더 큰 모델, 더 긴 프롬프트) 이 TTL을 고정값으로 두지
  말고 다시 검토해야 합니다.
- 룸 단위(사용자 단위도, 전역도 아님) 락 범위가 여기서는 맞는 선택입니다 — 전역 락은 관련 없는
  룸들의 AI 답장까지 아무 이유 없이 직렬화시키고, 사용자 단위 락은 이 문제의 원인인 동일 룸
  중복 트리거를 막지 못합니다.
