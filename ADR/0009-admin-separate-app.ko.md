# 0009: admin 대시보드를 완전히 별도 앱으로 분리 (`frontend`의 라우트가 아님)

## 상태

Accepted

## 배경

사용자/룸 관리, 모더레이션 액션, 감사 로그 내보내기에는 UI가 필요합니다. 독립 앱을 만드는 것의
대안은 기존 `frontend` 패키지 안에 보호된 라우트(예: `/admin`)를 두고 `protected-route.tsx`와
역할 검사로 가드하는 방식이었습니다. 그랬다면 코드베이스 하나, 번들 하나, Vercel 프로젝트
하나로 끝났을 것입니다.

## 결정

`admin/`은 독립된 pnpm 워크스페이스 패키지입니다. 자체 React 앱, 자체 `vercel.json`, 자체 Vercel
프로젝트, 자체 Playwright e2e 스위트(`admin/e2e/`, CI 잡 `admin-e2e`)를 가지며,
`graphql-ws`/`socket.io-client` 의존성이 아예 없습니다. GraphQL API에 query/mutation만 수행하고
실시간 채팅 전달에는 전혀 관여하지 않습니다([시스템 컨텍스트](../ARCHITECTURE.ko.md#시스템-컨텍스트)
다이어그램 참고).

- **이유:** 이 분리는 구체적으로 권한/보안 경계를 위한 것입니다. 개발자 본인의 설명에 따르면,
  admin 전용 코드를 일반 채팅 사용자에게 배포되는 번들 밖에 물리적으로 두면 admin 기능이 노출될
  수 있는 표면 자체가 구조적으로 줄어듭니다. `frontend` 안에 라우트 가드만 두는 방식은 admin UI
  코드(컴포넌트 트리, 뮤테이션 문자열, 모더레이션 액션 핸들러)를 어차피 모든 방문자의 브라우저
  번들로 내려보내고, 그걸 숨기는 일을 전적으로 런타임 검사에 맡깁니다. 별도 앱은 애초에 admin이
  아닌 사용자에게 그 코드를 내려보내지 않습니다.
- 고려했다가 배제한 대안:
  - **`frontend` 안의 보호된 `/admin` 라우트**(배경 절의 대안): 위 번들 노출 문제로
    배제했습니다. 코드베이스 하나, Vercel 프로젝트 하나라 운영 비용은 더 쌌겠지만, admin UI
    코드가 역할과 무관하게 모든 채팅 사용자의 브라우저로 내려갑니다.
  - **라우트 단위 코드 스플리팅**(admin 번들을 lazy 로딩해서 비관리자는 다운로드하지 않게):
    배제했습니다. lazy 청크도 결국 같은 오리진에서 서빙되고 경로를 아는 사람은 누구나 받을 수
    있습니다. 기본 노출을 줄일 뿐, 일반 사용자가 접근 가능한 배포물에서 코드를 실제로
    제거하지는 못합니다.

## 결과

- Vercel 프로젝트가 두 개이므로 모든 환경에서 `CORS_ORIGIN`에 항목 두 개를 유지해야
  하고([0005](0005-cors-multi-origin-policy.ko.md) 참고), 배포 파이프라인과 관측 대시보드도
  하나가 아니라 두 개를 따로 확인해야 합니다.
- 새로운 admin 전용 기능은 `frontend` 안에 역할 검사로 숨기지 말고 `admin/`에 두어야 합니다.
  `frontend`에 admin 라우트를 추가하면 이 분리가 피하려던 번들 노출 문제가 그대로 재발합니다.
- `admin/`에 실시간 의존성이 없는 것은 의도된 상태입니다. `frontend`와 "코드를 공유하기 위해"
  `graphql-ws`나 `socket.io-client`를 추가하는 것은 절대 제안하지 않습니다. 이 앱이 지켜야 할
  query/mutation 전용 경계가 흐려지기 때문입니다.
