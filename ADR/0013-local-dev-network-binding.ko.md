# 0013: 로컬 개발 서비스는 127.0.0.1에만 바인딩하고 Redis는 인증을 요구

## 상태

Accepted

## 배경

실제로 확인된 사고입니다: 로컬 Docker Compose 서비스들이 원래 `0.0.0.0:PORT:PORT`로 바인딩되어
모든 네트워크 인터페이스에 노출되어 있었습니다. 개발 머신의 이더넷 어댑터가 공인 IP를 가지고 있는
동안 Windows 방화벽 프로필이 "Private(신뢰됨)"으로 설정되어 있었고, 이는 어떤 포트로든 인바운드
연결을 허용하는 Docker Desktop 방화벽 규칙을 활성화시켰습니다. 그 결과 PostgreSQL(5432),
Redis(6379), 백엔드(3000)가 인터넷에서 접근 가능한 상태였고, 자동화된 랜섬웨어 봇이 기본 자격
증명으로 PostgreSQL에 접근해 데이터베이스를 지우고 `readme_to_recover` 데이터베이스에 몸값 요구
쪽지를 남겼습니다. 전체 경위는 README의
[AI 보조 개발 사례](../README.ko.md#ai-보조-개발-사례)에 정리되어 있습니다.

## 결정

- 모든 `docker-compose.yml` 포트 바인딩은 `0.0.0.0:PORT:PORT`가 아니라 `127.0.0.1:PORT:PORT`입니다
  (`docker-compose.yml:17-18, 31-32, 55-56` — backend, Postgres, Redis).
- `backend/src/main.ts`는 로컬/개발 환경에서 HTTP 리스너를 `127.0.0.1`에 바인딩합니다.
- Redis는 프로덕션뿐 아니라 로컬 개발에서도 비밀번호(`requirepass`)를 요구합니다.
- 이와 유사한 노출이 발생했을 때의 대응 순서는 네트워크 봉쇄 → 자격 증명 교체 → 유물 정리
  순입니다 — 이 사고 대응 중 실제로 따랐던 순서를 정식화한 CLAUDE.md의
  [Containment Before Cleanup](../CLAUDE.md#incident-response) 원칙을 참고하세요.

## 결과

- 다른 기기(예: 휴대폰으로 테스트)에서 로컬 개발 서버에 접근하려면 SSH 터널이나 명시적인
  포트 포워딩이 필요합니다(단순 `IP:port`로는 안 됨) — 확인된 공격 경로를 막은 대가로 받아들인,
  실질적이지만 작은 불편입니다.
- "편의를 위해"(예: 다른 기기에서 테스트하려고) 어떤 `docker-compose.yml` 포트 바인딩이든
  `0.0.0.0`으로 되돌리는 것은 절대 제안하지 않습니다 — 이것이 바로 위에서 확인된 데이터 손실
  사고로 이어진 그 설정이며, 가상의 위험이 아닙니다.
- 로컬 개발을 포함한 어떤 환경에서도 `requirepass` 없이 Redis를 실행하는 것은 절대 제안하지
  않습니다 — 이 사고는 구체적으로 자격 증명 없이 접근 가능했던 서비스와 관련이 있었습니다.
- `docker-compose.yml`에 새로 추가되는 서비스는 기본적으로 `127.0.0.1:PORT:PORT` 바인딩을
  써야 합니다. Docker가 모든 인터페이스에 바인딩해버리는 단순 `PORT:PORT`는, 이 프로젝트에서는
  `CORS_ORIGIN: '*'`와 마찬가지로 Never Do Group 3에 준하는 위반입니다.
