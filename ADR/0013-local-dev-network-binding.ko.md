# 0013: 로컬 개발 서비스는 127.0.0.1에만 바인딩하고 Redis는 인증을 요구

## 상태

Accepted

## 배경

실제로 겪은 사고입니다. 로컬 Docker Compose 서비스들이 원래 `0.0.0.0:PORT:PORT`로 바인딩되어
모든 네트워크 인터페이스에 노출되어 있었습니다. 하필 개발 머신의 이더넷 어댑터가 공인 IP를 가진
상태에서 Windows 방화벽 프로필이 "Private(신뢰됨)"으로 잡혀 있었고, 그 프로필이 어떤 포트로든
인바운드 연결을 허용하는 Docker Desktop 방화벽 규칙을 활성화했습니다. 그 결과 PostgreSQL(5432),
Redis(6379), 백엔드(3000)가 인터넷에서 접근 가능했고, 자동화된 랜섬웨어 봇이 기본 자격 증명으로
PostgreSQL에 들어와 데이터베이스를 지운 뒤 `readme_to_recover` 데이터베이스에 몸값 요구 쪽지를
남겼습니다. 전체 경위는 README의
[AI 보조 개발 사례](../README.ko.md#ai-보조-개발-사례)에 정리되어 있습니다.

## 결정

- 모든 `docker-compose.yml` 포트 바인딩은 `0.0.0.0:PORT:PORT`가 아니라 `127.0.0.1:PORT:PORT`입니다
  (`docker-compose.yml:17-18, 31-32, 55-56` — backend, Postgres, Redis).
- `backend/src/main.ts`는 맨몸으로 `pnpm start:dev`를 실행할 때(`NODE_ENV=development`)만 HTTP
  리스너를 `127.0.0.1`에 바인딩합니다. 이는 그 특정 로컬 실행 경로만을 위한 별도의 방어
  조치이지, 위 사고를 막은 요인이 아닙니다. `docker-compose`(`NODE_ENV=docker`)에서는 컨테이너가
  Docker 네트워크에서 오는 연결을 받아야 하므로 `main.ts`는 내부적으로 일부러 `0.0.0.0`을
  유지합니다. 즉 docker-compose 쪽 노출은 순전히 포트 매핑 변경만으로 막힌 것이지, 이 인프로세스
  바인딩 덕분이 아닙니다(`main.ts:100-103`의 인라인 주석 참고).
- Redis는 프로덕션뿐 아니라 로컬 개발에서도 비밀번호(`requirepass`)를 요구합니다.
- 비슷한 노출이 또 발생하면 대응 순서는 네트워크 봉쇄 → 자격 증명 교체 → 잔여물 정리입니다.
  이 사고 대응에서 실제로 따랐던 순서를 정식화한 CLAUDE.md의
  [Containment Before Cleanup](../CLAUDE.md#incident-response) 원칙을 참고하세요.
- 고려했다가 배제한 대안:
  - **`0.0.0.0` 바인딩을 유지하고 Windows 방화벽에만 의존**: 배제했습니다. 실제 사고에서
    정확히 이것이 실패했습니다(방화벽 프로필이 "Private/신뢰됨"으로 잘못 설정되어 있었음).
    애플리케이션/포트 매핑 레벨에서 `127.0.0.1`로 바인딩하는 것은 방화벽 상태가 올바르다는
    가정에 기대지 않는 다층 방어입니다.
  - **localhost 전용 바인딩 + 필요 시 수동 포트 포워딩 대신, VPN 전용 접근**(예: Tailscale):
    진행하지 않았습니다. 같은 문제를 풀 수는 있지만, 이 프로젝트의 실제 필요(개발자 1인이
    가끔 휴대폰으로 테스트)에 비해 상시적인 설정/유지보수 부담이 더 큽니다.

## 결과

- 다른 기기(예: 휴대폰 테스트)에서 로컬 개발 서버에 접근하려면 단순 `IP:port`로는 안 되고 SSH
  터널이나 명시적인 포트 포워딩이 필요합니다. 확인된 공격 경로를 막은 대가로 받아들인, 작지만
  실재하는 불편입니다.
- "편의를 위해"(예: 다른 기기에서 테스트하려고) `docker-compose.yml`의 포트 바인딩을
  `0.0.0.0`으로 되돌리는 것은 절대 제안하지 않습니다. 바로 그 설정이 위에서 확인된 데이터 손실
  사고로 이어졌으며, 가상의 위험이 아닙니다.
- 로컬 개발을 포함한 어떤 환경에서도 `requirepass` 없는 Redis 실행은 절대 제안하지 않습니다.
  이 사고의 핵심이 바로 자격 증명 없이 접근 가능했던 서비스였습니다.
- `docker-compose.yml`에 새로 추가하는 서비스는 기본적으로 `127.0.0.1:PORT:PORT` 바인딩을
  써야 합니다. Docker가 모든 인터페이스에 바인딩해버리는 단순 `PORT:PORT`는, 이 프로젝트에서는
  `CORS_ORIGIN: '*'`와 마찬가지로 Never Do Group 3에 준하는 위반입니다.
