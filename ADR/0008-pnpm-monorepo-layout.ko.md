# 0008: pnpm 워크스페이스 모노레포 (backend/frontend/admin)

## 상태

Accepted

## 배경

이 프로젝트는 결국 하나의 GraphQL 계약을 공유하는 세 개의 배포 단위가 필요해졌습니다: NestJS
백엔드, 채팅 프론트엔드, 그리고 (나중에 추가된) 별도의 admin 대시보드
([0009](0009-admin-separate-app.ko.md) 참고). 각각을 별도 저장소로 둘 수도 있었고, 셋 다 한
저장소를 공유할 수도 있었습니다.

## 결정

- 저장소 하나, 루트 `pnpm-lock.yaml` 하나, `pnpm-workspace.yaml`에 선언된 워크스페이스 패키지
  세 개: `backend`, `frontend`, `admin`.
- 루트 레벨 스크립트(`package.json`)는 `backend`로만 프록시합니다(`pnpm build` →
  `pnpm --filter backend build` 등) — `frontend`/`admin`은 각자 디렉터리 안에서 직접 실행합니다.
- **이유:** 1인 프로젝트 규모 — 개발자 한 명이 GraphQL 계약을 공유하는 패키지 3개를 관리할 때는
  모노레포 쪽 오버헤드가, 별도 저장소 세 개를 조율하며 계약을 수작업으로 맞추는 것보다 낮습니다
  (개발자 본인 표현: "1인 프로젝트 규모에 적합하고, 관리가 편리하며, 관리 비용이 적음").

## 결과

- 루트 락파일 하나가 세 패키지의 의존성 해석을 모두 묶습니다 — 런타임 코드를 공유하지 않는데도, 한
  패키지의 의존성 트리에서 버전이 하나 올라가면 다른 패키지가 해석하는 버전이 바뀔 수 있습니다.
- CI(`.github/workflows/deploy.yml`)는 변경된 경로 기준으로 잡을 필터링하지 않습니다 — 실제로
  어느 패키지가 바뀌었든 매 push마다 `backend` lint+test와 `admin-e2e` 잡이 둘 다 돕니다. 지금
  규모에서는 받아들일 만하지만, 팀이나 패키지 수가 늘어나면 Nx/Turborepo류의 영향받은-패키지 필터링이
  필요해질 것입니다.
- 명시적 요청 없이 `backend`/`frontend`/`admin`을 별도 저장소로 쪼개는 것은 절대 제안하지 않습니다
  — 이 구조가 애초에 피하려던 조율 비용(`schema.gql`과 클라이언트 오퍼레이션을 여러 저장소에 걸쳐
  맞추기, 공유 패키지 버전 관리)을 그대로 다시 만들어버립니다.
- 네 번째 워크스페이스 패키지(예: 향후 모바일 클라이언트)를 추가할 때는, 빌드/배포 요구사항이
  pnpm 워크스페이스 모델과 정말로 맞지 않는 경우가 아니라면 새 저장소를 시작하지 말고 동일한
  `pnpm-workspace.yaml`에 추가하는 것을 기본으로 삼아야 합니다.
