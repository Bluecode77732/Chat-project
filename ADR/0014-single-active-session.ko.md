# 0014: 사용자당 활성 세션 하나만 유지 (이전 소켓 자동 축출)

## 상태

Accepted

## 배경

`SessionCacheService`는 Redis에서 사용자당 하나의 `userId → {socketId, status}` 매핑을
추적합니다. 축출 규칙이 없다면 사용자가 두 번째 탭이나 기기를 열 때 같은 `userId`로 두 번째
소켓이 등록되고, 두 소켓 모두 독립적으로 "그" 사용자의 연결로 취급됩니다. 그러면 원래 세션
하나만 받아야 할 `forceLogout`/룸 충돌 이벤트를 둘 다 받거나, 사용자가 더는 활성으로 여기지
않는 오래된 소켓으로 룸 브로드캐스트가 흘러갈 수 있습니다.

## 결정

`ChatGateway.handleConnection()`이 호출하는 `ChatService.registerClient()`는 새 소켓을 먼저
현재 세션으로 기록하고, 같은 사용자에 대해 이전에 다른 소켓이 등록되어 있었다면 그다음에
`kickPreviousSession()`(`chat.service.ts:57-62`)을 호출합니다. 이 함수는 대체된 소켓에
`forceLogout` 이벤트를 emit하고 연결을 끊습니다. "먼저 기록하고 나중에 축출"하는 순서는
의도된 것입니다. 반대로 새 세션을 기록하기 전에 이전 소켓을 먼저 끊으면, 이전 소켓의
disconnect 핸들러(`removeClient`, `chat.service.ts:65-69`)가 새 세션의 온라인 상태를 도로
오프라인으로 덮어쓰는 레이스가 생깁니다(`chat.service.ts:41-46`의 인라인 주석 참고).
- 고려했다가 배제한 대안:
  - **사용자당 여러 동시 세션 허용, 축출 없음**: 배경 절에서 서술한 기존 문제 그 자체라 실행
    가능한 선택지가 아닙니다. 두 소켓이 세션 하나 몫의 이벤트를 각자 받고, 오래된 소켓이
    사용자가 더는 보지 않는 룸 브로드캐스트를 계속 받게 됩니다.
  - **이전 연결을 축출하는 대신 새 연결을 거부**: 배제했습니다. "새 기기에서 로그인"이 아예
    실패하고, 이미 방치됐을지도 모르는 이전 세션이 자리를 계속 차지합니다. 흔한 경우(사용자가
    새 세션을 열면 보통 그 세션이 이기길 원함)에 오히려 더 나쁩니다.

## 결과

- 어느 시점이든 사용자당 라이브 소켓은 최대 하나입니다. 이 기존 Socket.IO 경로뿐 아니라
  새로 만드는 사용자별 실시간 등록도 똑같이 이전 등록을 확인하고 축출해야 하며, 다른 곳에서
  사용자당 연결 하나가 보장된다고 가정하면 안 됩니다.
- 대체된 세션의 프론트엔드는 조용히 끊기는 대신 명시적인 `forceLogout` 이벤트를 받습니다. 이
  이벤트를 먼저 emit하지 않고 이전 소켓을 끊는 것은 절대 제안하지 않습니다. 프론트엔드는
  설명 없이 끊기는 대신 "다른 곳에서 로그인됨" 상태를 보여주기 위해 이 이벤트에 의존합니다.
- `registerClient`의 순서를 바꿔 새 세션 기록 전에 이전 세션을 먼저 축출하는 것도 절대
  제안하지 않습니다. 현재 순서가 막고 있는 바로 그 레이스가 도로 열립니다(`chat.service.ts:41-46`의
  인라인 주석 참고).
